# Hetzner local backup and isolated restore

The owner-approved scope is an actual encrypted backup and isolated restore on the existing Hetzner staging PostgreSQL container. Off-host backups and recovery are deferred. This helper does not establish production RPO/RTO, host-loss recovery or a production restore.

Run `deploy/hetzner/restore-drill.mjs` from the reviewed full checkout on the authorized server. It accepts only the generated `av8-delivery-staging` project, its explicit staging database/owner/resource, a non-published database on one internal project network, and an existing running API image. There is no production override or caller-selected restore target. No source table, role, account, password, MFA enrollment, provider configuration or Compose service is modified.

Before starting, the release owner must hold staging writers for the duration: no UI mutations, worker invocations, scheduler/monitor writes or parallel acceptance scripts. `--writers-quiesced` records that operational assertion; the helper also compares source table and sequence manifests before/after the dump and after restored-API verification. Any intervening source change fails the drill instead of being ignored. Read-only host/API health checks may continue.

The current named owner's private JSON may contain `{email,password}` or `{email,temporaryPassword}`. The initial-owner file is valid only while its temporary password has not expired or been replaced. Its contents must never be pasted into commands/logs. The helper copies credentials only into its private disposable directory and reads the MFA encryption key from the existing private source configuration. These are never printed or placed in Docker command arguments/environment variables.

```sh
node deploy/hetzner/restore-drill.mjs \
  --private-directory /srv/av8-erp-final/staging/private \
  --backup-directory /srv/av8-erp-final/backups/staging \
  --evidence-directory /srv/av8-erp-final/recovery-evidence/staging \
  --credentials-file /srv/av8-erp-final/staging/private/bootstrap/initial-owner.json \
  --writers-quiesced
```

The command retains the actual `backup.mjs` AES-256-GCM archive and its digest manifest in the backup directory, with the existing operational `backup-key` unchanged in private configuration. It never substitutes an ephemeral drill-only key. Backups and evidence are owner-only and separate from private configuration. The plaintext decrypted dump is mode 0600 and removed after restoration or failure cleanup.

The restore uses a random `av8_staging_restore_<24-hex>` database on the same dedicated staging PostgreSQL container. It reuses the original owner and restricted runtime roles without changing role privileges or memberships. A fresh PostgreSQL database already contains an empty `public` schema, while the schema-scoped dump creates that schema itself. The helper drops only the empty `public` schema in its newly created, identity-checked recovery target, without CASCADE; unexpected existing objects stop preparation. `pg_restore --exit-on-error --no-owner --role=<original-owner>` then preserves schema grants, policies, sequences and data; a distinct recovery environment marker is provisioned outside the restored public schema. Required source migrations must match the checkout, with at least one application, progress record and private AV8 attachment present.

Before login changes anything in the restored copy, the helper compares every public table's row count and deterministic row-content hash, every public sequence's value/state, attachment byte counts/SHA256 values, and posted-journal balance. These checks cover database-backed attachments as well as records. A clean restore is rejected if any source document content does not match its stored length/hash.

A temporary API container then starts from the exact currently running staging image ID. It has no published port and only the internal database network, no provider credentials, fresh token/scheduler signing secrets, the original MFA decryption key, disabled email/alerts/workers/scheduler and no bootstrap configuration. Startup must verify its recovery database/resource marker, original admin identity, restricted runtime privileges and effective RLS.

Actual HTTP acceptance covers health, password login that requires MFA, MFA completion, `/auth/me`, authenticated private-document bytes and unauthenticated document denial. If the restored initial owner is unenrolled or must change a temporary password, the helper enrolls MFA and completes an authenticated step-up/password change **only in the restored database**, then logs in again. It privately reads the restored encrypted MFA secret to compute TOTP; no MFA secret, password, recovery code or token is emitted. Runtime database checks independently verify unscoped tenant/document invisibility, scoped attachment bytes and wrong-tenant denial.

The final private `evidence.json` reports measured time, source/target identities, exact API image, archive hashes, table/sequence/document counts, data-manifest hash, authentication/document/RLS outcomes and cleanup status. Creation, empty-schema preparation, restore and comparison have distinct phases. Failed child-command stderr is retained only in owner-only `diagnostics/` files; public evidence contains a fixed failure classification and path, never raw stderr or command arguments. A successful archive manifest is updated with `restoreVerified:true` and the evidence path. This status must not be asserted from unit tests alone. Public handover evidence should copy only the redacted result, never the archive, key, credential file, raw database contents, private diagnostics or temporary configuration.

Cleanup deletes only the helper's uniquely named recovery API container, recovery database and copied secrets/plaintext dump. It does not prune images, remove volumes, run `down`, reset source data or delete the retained archive/key/evidence. `ownership.json` is written before resource creation. If the process is forcibly killed or cleanup fails, inspect that receipt and the exact `av8.recovery.resource` container label before removing only those named recovery resources; never apply wildcard deletion or use source database/project names. Preserve failure evidence and encrypted backup.

Local preparation evidence: ten guard/encryption tests passed, including tamper rejection, generated-target-only schema preparation without CASCADE, fixed diagnostic classification and proof that a wrong actual Compose project triggers no backup/create/drop commands or credential output. The manifest/sequence/document/journal SQL was validated in a read-only transaction against isolated local test data:71 tables,57 sequences,518 AV8 attachments, no invalid documents or unbalanced journals. First actual server execution retained a 559,101-byte encrypted backup but failed on the pre-existing empty public schema; source was preserved and cleanup passed.

After the target-only correction, the candidate host rerun passed in 15.317 seconds; its original evidence is preserved in [candidate recovery evidence](evidence/hosted-local-recovery-candidate.json). The final exact application image `170b929bd4749e3ae53c7dcb0155e90d617210d9` then passed a fresh drill in **15.535 seconds**: 43 migrations, 71 tables, 57 sequences, 588 rows and one 1,487-byte PDF matched, with zero unbalanced journals. Actual API restart/health, named-owner password/MFA, scoped HTTP PDF bytes, anonymous/wrong-tenant denial and unchanged source all passed. Temporary recovery resources were removed; the operational encrypted archive and original key remain retained. [Final host evidence](evidence/hosted-local-recovery.json) records exact images and hashes. Production separately has a successful encrypted local backup and daily timer; production-data restoration was not exercised. No off-host recovery or production RPO/RTO claim is made.
